# WonderFleet — operations runbook

## Health

| Probe | Path | Meaning |
|---|---|---|
| Liveness | `/health/live` | The process is up. Render restarts the instance if this fails. |
| Readiness | `/health/ready` | Includes a PostgreSQL round trip. |

## First deployment (Render)

1. Create the blueprint from `deploy/render.yaml`.
2. Set the secrets marked `sync: false`: `Seed__AdminPassword`, `Firebase__ServiceAccountJson`,
   `Google__ApiKey`, `OpenAi__ApiKey`, `Email__ApiKey`, `Sms__Termii__ApiKey`, `Telemetry__WebhookSecret`.
3. Deploy. The first boot applies `V001__initial_schema.sql` and seeds the administrator.
4. Sign in and change the seeded password immediately (the account is flagged must-change-password).
5. Register the devices (`POST /api/v1/devices`) using the Firebase keys the hardware writes under `vehicles/`.

> The signing keys are generated by Render on first deploy. **Changing them signs everyone out** and
> invalidates existing share links; rotate deliberately.

## Daily checks

- Dashboard sync banner: "All sensors transmitting" with a recent sync time.
- `GET /api/v1/devices/unknown-keys`: hardware publishing data that nobody has registered yet.
- `GET /api/v1/alerts/summary`: open criticals should trend to zero.

## Common situations

**"Sensors last synced N minutes ago".**
Check `Telemetry:PollingEnabled`, then `Firebase:DatabaseUrl` and the service-account secret. The poller logs
one warning per failed cycle. Devices themselves are marked offline by the monitor after the configured
minutes without data.

**A device's limits did not reach the hardware.**
The API raises an in-app hardware notification when the push fails. Use
`POST /api/v1/devices/{id}/sync-thresholds` once the device is online again.

**Emails or SMS are not arriving.**
Deliveries live in `notification_deliveries`. Rows with `status = 'Failed'` carry `last_error`.
Pending rows retry automatically (30 s → 8 min, 6 attempts). Check the provider keys first:

```sql
select channel, status, count(*), max(last_error)
from notification_deliveries
where created_at > now() - interval '1 day'
group by 1, 2;
```

**A partner says their link stopped working.**
Expected once every trip on the link has ended, at `expires_at`, or after a revoke or a suspension.
Check `share_links.revoked_at`, `expires_at`, and the partner's status, then generate a new link.

**A shipment is stuck "Scheduled".**
It needs a device before it can start: `PUT /api/v1/trips/{id}/assignment`, then `POST /api/v1/trips/{id}/start`.

**Route AI answers with `model: wonderfleet-heuristic-v1`.**
The language model was unavailable or its answer failed validation; the deterministic fallback ran. Check
`OpenAi__ApiKey` and the logs. This is a degraded mode, not an outage.

**Fuel estimates look wrong.**
Check the inputs before the model: `confidence` on the estimate says what was available. `Low` means neither
traffic nor forecast could be fetched, so check `Google__ApiKey` and the Routes and Weather APIs. If the
figure is consistently high or low for one partner, record their measured consumption on the vehicle
(`baselineLitresPer100Km`) — a real figure always beats the modelled baseline. Pump prices are maintained in
Settings; changing one does not rewrite estimates already made.

```sql
-- planned versus actual fuel, last 30 days
select v.fleet_number, t.trip_code, t.planned_fuel_litres, t.actual_fuel_litres,
       round(t.actual_fuel_litres - t.planned_fuel_litres, 1) as variance_l
from trips t join vehicles v on v.id = t.vehicle_id
where t.actual_fuel_litres is not null and t.loading_time > now() - interval '30 days'
order by abs(t.actual_fuel_litres - t.planned_fuel_litres) desc;
```

## Database

Migrations are applied automatically on boot (`V001` schema, `V002` fuel planning). To add a change, create
`db/migrations/V003__*.sql` —
**never edit an applied file**: the checksum guard will stop the app on the next deploy.

**Supabase:** use the session pooler host, set `Database__SslMode=Require`, and set
`Database__TransactionPooling=true` only if you are on the 6543 transaction pooler. A
`gin_trgm_ops does not exist` error means the extensions schema is off the search path — check
`Database__SearchPath`. A free-tier project that has paused will time out on the first request.

Backups: Render's managed Postgres handles them; on Supabase, check the backup schedule for your
plan (free projects keep a shorter window). Before any risky change, take a manual snapshot.

Useful queries:

```sql
-- telemetry volume per device today
select d.serial, count(*) from sensor_readings r
join devices d on d.id = r.device_id
where r.recorded_at > current_date group by 1 order by 2 desc;

-- open alerts by type
select alert_type, severity, count(*) from alerts where status <> 'Resolved' group by 1, 2;

-- live share links
select audience, count(*) from share_links
where revoked_at is null and expires_at > now() group by 1;
```

## Scaling notes

The poller, the monitor and the outbox dispatcher all take PostgreSQL advisory locks, so running several web
instances is safe: exactly one instance does each job per cycle.
